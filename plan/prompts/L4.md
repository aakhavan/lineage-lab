# L4: OpenLineage events from dbt

Contract: `docs/spec.md` section 5. Rules: `AGENTS.md`. Needs both stacks, the test bed and the work copy.

Build:
1. `src/lineagelab/olrun.py`: `python -m lineagelab.olrun` runs `dbt-ol build` (package `openlineage-dbt`, in an isolated environment with dbt-core 1.12 and dbt-postgres) on the work copy, target `dev`, namespace `lineagelab`, so that the events reach Marquez and are saved unedited to `artifacts/openlineage/events.ndjson`. Find out from the OpenLineage Python client docs how to do both (the spec lists the options) and whether column lineage needs to be switched on. One JSON line: events saved, jobs seen in Marquez.
2. `src/lineagelab/olevents.py`: `load(path)`, `summary(events)`, `edges(events)` as the spec says; pure functions.
3. `src/lineagelab/olforward.py`: `python -m lineagelab.olforward` posts the saved events to OpenMetadata's OpenLineage endpoint and reports per event what happened; then looks at whether lineage appeared on `shop_testbed` tables. This is an experiment: write `docs/findings/openlineage-to-openmetadata.md` (what was sent, what was accepted, what resolved to tables and what did not, why, and what naming or mapping would fix it). Never add lineage through another API to make it look as if it worked.
4. Record tool versions in `stack/versions.yaml`.

Tests (offline, on a small hand-made events fixture in `tests/fixtures/` with invented names): `test_summary_counts_runs_jobs_datasets_and_facets`, `test_edges_come_from_complete_events_only`, `test_column_edges_come_from_the_column_lineage_facet`, `test_load_skips_blank_and_broken_lines_and_counts_them`.

Done when `plan/accept/accept_l4.py` passes.
